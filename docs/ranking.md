# 土拨鼠输入法排序算法

## 概述

土拨鼠输入法使用**层级 Frecency** 排序算法，结合以下两个核心机制：

1. **层级系统** - 基于匹配类型（完全/前缀）和编码类型（五笔/拼音/英文）的绝对优先级
2. **Frecency 分数** - 层级内部基于时效性 + 使用频率 + 基础词频的排序

```
总分 = 层级加成 + 层级覆盖加成 + 时效分 + 频率分 + 基础分 + 短词加成
```

---

## 层级系统（绝对优先级）

层级系统提供**绝对优先级** - 高层级候选词始终排在低层级之上，无论 Frecency 分数如何。

### 保护层级 - 简码保护

五笔简码拥有**两级保护层级**，**不能被**用户学习数据覆盖。保护层级基于 `jianma.txt` 中定义的官方简码：

| 层级 | 定义 | 加成 | 可覆盖 |
|------|------|------|--------|
| P0 | 一级简码（jianma.txt 中 1 字符编码） | +10T | ❌ 永不 |
| P1 | 二级简码（jianma.txt 中 2 字符编码） | +1T | ❌ 永不 |

**判断逻辑**：只有当 `(输入编码, 候选词)` 组合在 `jianma.txt` 中明确定义时，才会获得保护层级加成。这确保：
- `b` → `了` 获得 P0 保护（10T），因为 `b 了` 在 jianma.txt 中
- `b` → `子` 不获得保护，即使 `子` 是 `bb` 的二级简码

**设计理由**：一级简码（25 个单键编码，如 `i`→我、`w`→人）和二级简码（625 个双键编码）是五笔输入的核心效率所在。这些编码已深深刻入用户的肌肉记忆 - 用户期望它们**永远**产生相同的结果。如果允许 Frecency 或用户历史重新排序这些简码，将破坏五笔快速输入的确定性本质。

**实现方式**：
- 一级简码加成（10T）高于二级简码加成（1T）+ 最大 boost（~501B）
- 二级简码加成（1T）高于第1层加成（100B）+ 层级覆盖加成（500B）= 600B

这确保：
1. 一级简码**永远**排在二级简码之上
2. 二级简码**永远**排在其他候选词之上

### 短码模式（输入长度 <= 4）

当输入为 4 个字符或更少时，优先匹配五笔。这些是**常规层级**，可以被用户选择覆盖：

| 层级 | 匹配类型 | 编码类型 | 加成 | 可覆盖 |
|------|----------|----------|------|--------|
| 1 | 完全匹配 | 五笔（3-4字符）/ 英文 | +100B | ✅ 可以 |
| 2 | 完全匹配 | 拼音 | +10B | ✅ 可以 |
| 3 | 前缀匹配 | 五笔 | +1B | ❌ 不吃层级覆盖加成 |
| 4 | 前缀匹配 | 拼音 | 0 | ✅ 可以 |

**注意**：
- 1-2 字符的五笔完全匹配属于第 0 层（保护层级），而非第 1 层。
- 英文候选的分数只决定英文之间的先后；它相对五笔、拼音候选的位置另有规则，见下面的「英文匹配」。
- 第 3 层（五笔前缀）不加层级覆盖加成。这个加成按词条记录，不区分当时输入的是哪个码：在 `uqwy` 选了「交集」，如果加成也作用于前缀匹配，输入 `uqw` 时「交集」会挤掉三码精确匹配「次」，持续约 2 小时。时效分和频率分仍然生效，只影响前缀词之间的先后。

**设计理由**：3-4 字符的五笔编码（三级简码、全码）可以被覆盖，因为用户可能确实偏好其他词。但 1-2 级简码受到保护。

### 长码模式（输入长度 > 4）

当输入超过 4 个字符时，仅匹配类型影响排序：

| 层级 | 匹配类型 | 加成 | 可覆盖 |
|------|----------|------|--------|
| 1 | 完全匹配（拼音/英文） | +100B | ✅ 可以 |
| - | 英文前缀匹配（补全） | +1B，只用于英文之间排序 | ❌ 不吃层级覆盖加成 |
| 2 | 拼音前缀匹配 | 0 | ✅ 可以 |

**设计理由**：超过 4 个字符的输入不可能是五笔编码，只可能是拼音或英文单词。完全匹配排在最前。

### 英文匹配

英文按输入的大小写分两种情况处理，目标是英文可用但不占中文候选的位置。

**全小写：英文只占每页最后一位。** 只要列表里有五笔或拼音候选，英文候选（完全匹配和补全都算）就只出现在每一页的最后一位：排序后第一个英文候选在第 1 页末位，第二个在第 2 页末位，依此类推。中文候选保持原有顺序，填每页前面的位置。

| 输入 | 每页 7 个候选时 |
|------|----------------|
| `the` | 第 1–6 位是五笔候选，第 7 位是 `the` |
| `kuber` | 第 1–6 位是拼音候选，第 7 位是 `Kubernetes`；第 2 页的第 7 位是下一个补全 |
| 2 个中文候选 + 3 个英文候选 | 中、中、英、英、英（中文用完后英文依次接在后面） |
| `kubernetes`（没有中文候选） | 全是英文，按分数排 |

这样空格上屏的永远是中文候选，「上屏英文候选」键（默认 Tab）上屏当前页的那个英文候选；当前页没有英文候选时这个键不起作用。

分数（包括刚选过的词拿到的层级覆盖加成和时效分）只决定哪个英文词落在更靠前的页，不会让英文离开页尾。实现上是排序之后的一步独立处理（`CandidateRanker.placeEnglishAtPageEnds`），不改分数。列表里只有英文、或没有英文时，这一步什么也不做。

小写输入什么时候给英文补全：

| 输入 | 英文完全匹配 | 英文前缀补全 |
|------|--------------|--------------|
| 4 个字母以内 | 给 | 不给；五笔和拼音都没有候选时才给 |
| 5 个字母以上 | 给 | 最多 3 个 |

**含大写字母：只出英文。** 大写字母表示用户明确在打英文，候选里不出现五笔和拼音，包括一、二级简码。列表里有：

- 词表里的完全匹配和最多 3 个补全，大小写跟随输入；
- 用户自己加的英文词（它们在数据库里按拼音存，文本是纯 ASCII 的词条会被保留并按英文处理）；
- 最后一位是输入本身。词表里没有的词（如 `Marmotim`）因此仍有一个候选，按空格原样上屏，而不是因为没有候选被清掉。

| 输入 | 候选 |
|------|------|
| `Wor` | World、Work、Word、Wor |
| `WOR` | WORLD、WORK、WORD、WOR |
| `github` / `GITHUB` | GitHub（词表里自带大小写的词始终按词表写法） |
| `Marmotim` | Marmotim |

**词频决定英文之间的先后。** 每个英文词的基础分由它的词频名次换算（名次 1 → 60000，名次 80000 → 20000，下限 5000）。英文不使用短词加成，否则字母少的词会无条件靠前。

**每个英文词单独学习。** 英文词条不在数据库里，查询时从词表生成，词条 ID 由「键 + 显示形式」哈希得到，落在 `0x40000000`–`0x7FFFFFFF`（系统词条之上，用户词条 `0x80000000` 之下）。同一个词在任何机器上 ID 相同，选词记录按词保存。英文前缀匹配不吃层级覆盖加成，理由与五笔前缀相同：选过 `kubernetes` 不应该让它在每个更短的前缀下都排到其他补全之前。

**4 个字母以内的英文词只收常用的。** 这些词与五笔共用键位，词表在生成时就做了筛选，见 [vocab/SOURCES.md](../vocab/SOURCES.md)。5 个字母以上不受限制。

**词库来源**：英文词库存储在 `en_table.txt`，约 7.1 万条，由 `tools/build_en_table.py` 生成。

## Frecency 算法

在每个层级内，候选词按 Frecency 排序 - 结合**时效性**和**使用频率**。

### 时效分（指数衰减）

```swift
时效分 = 1,000,000,000 × e^(-λ × 时间间隔)
```

其中：
- `λ = ln(2) / 86400`（半衰期 = 1 天 = 86400 秒）
- `时间间隔` = 距离上次选择的秒数

**衰减曲线：**

| 距上次选择时间 | 时效分 | 初始值百分比 |
|----------------|--------|--------------|
| 刚刚选择 | 1,000,000,000 | 100% |
| 6 小时 | 757,858,283 | 75.8% |
| 12 小时 | 574,349,177 | 57.4% |
| 1 天 | 500,000,000 | 50% |
| 2 天 | 250,000,000 | 25% |
| 7 天 | 7,812,500 | 0.78% |
| 14 天 | 61,035 | 0.006% |

**关键特性**：选择后立即，时效分（约 10 亿）压倒所有其他因素，保证被选词在其层级内排第一。

### 频率分（永久累积）

```swift
频率分 = 选择次数 × 5,000,000
```

- 每次选择永久增加 5,000,000 分
- 永不衰减
- 足够多次选择后，频率分将超过衰减后的时效分

**示例：**

| 选择次数 | 频率分 |
|----------|--------|
| 1 | 5,000,000 |
| 10 | 50,000,000 |
| 100 | 500,000,000 |
| 1000 | 5,000,000,000 |

### 基础分（词典默认）

```swift
基础分 = 基础词频  // 0-65535
```

基础词频来自词典，反映：
- **五笔词条**：编码长度优先（编码越短，词频越高）
  - 1 字符编码（一级简码）：65,000
  - 2 字符编码（二级简码）：55,000
  - 3 字符编码（三级简码）：45,000
  - 4 字符编码（全码）：35,000

- **拼音词条**：词典位置优先（位置越靠前，词频越高）
  - 位置 0：65,000
  - 位置 1：64,500
  - 位置 2：64,000
  - ...每个位置递减 500

### 短词加成

```swift
短词加成 = (5 - 词长) × 10,000  // 如果词长 < 5
```

在同一层级内优先短词：
- 1 字词：+40,000
- 2 字词：+30,000
- 3 字词：+20,000
- 4 字词：+10,000
- 5 字及以上：0

**特例：五笔 4 码完全匹配**

当输入为五笔 4 码且完全匹配时，2 字词优先于 1 字词：
- 2 字词：+50,000（而非默认的 +30,000）
- 1 字词：+40,000

**设计理由**：五笔 4 码通常用于输入 2 字词（每字取 2 码）。用户输入完整 4 码时，更可能是想输入 2 字词而非单字的全码。

## 层级覆盖加成（跨层级提升）

一种特殊的高值加成，可以临时覆盖**常规层级**边界：

```swift
层级覆盖加成 = 500,000,000,000 × e^(-λ × 时间间隔)
```

其中：
- `λ = ln(2) / 3600`（半衰期 = 1 小时）
- 初始加成 = 500B（超过层级差距 100B）

**用途**：当用户反复选择拼音词而非五笔词时，层级覆盖加成允许拼音词临时排在五笔词之上。

**重要**：此加成**不能**覆盖保护层级（P0/P1 简码），也不作用于短码模式下的五笔前缀匹配（第 3 层）。
- P0（一级简码）加成（10T）高于 P1 加成（1T）+ 最大 boost（~501B）
- P1（二级简码）加成（1T）高于最大可能的常规分数（第1层 100B + 层级覆盖 500B = 600B）

这确保简码始终按官方定义的优先级排列。

**衰减：**

| 时间间隔 | 加成 | 效果 |
|----------|------|------|
| 刚刚 | 500B | 覆盖层级 |
| 30 分钟 | 354B | 仍可覆盖 |
| 1 小时 | 250B | 仍可覆盖 |
| 2 小时 | 125B | 勉强覆盖 |
| 3 小时 | 62.5B | 无法覆盖 |

**截止**：当加成低于 1B 时设为 0（不再有意义）。

## 分数计算示例

### 场景 1：刚选择的五笔词

```
输入："wo"（2 字符，短码模式）
匹配：五笔完全匹配，刚选择，基础分=55000

层级加成 = 100,000,000,000（第 1 层：五笔完全匹配）
层级覆盖加成 = 500,000,000,000
时效分 = 1,000,000,000
频率分 = 5,000,000（1 次选择）
基础分 = 55,000
短词加成 = 30,000（2 字词）

总分 = 601,005,085,000
```

### 场景 2：高频使用的拼音词

```
输入："wo"（2 字符）
匹配：拼音完全匹配，100 次选择，上次选择 2 天前

层级加成 = 10,000,000,000（第 2 层：拼音完全匹配）
层级覆盖加成 = 0（已衰减至截止值以下）
时效分 = 250,000,000（2 天 = 50% × 50%）
频率分 = 500,000,000（100 × 5,000,000）
基础分 = 60,000
短词加成 = 30,000

总分 = 10,750,090,000
```

### 场景 3：从未选择的默认词

```
输入："wo"
匹配：拼音前缀匹配，从未选择，基础分=40000

层级加成 = 0（第 4 层：拼音前缀匹配）
层级覆盖加成 = 0
时效分 = 0
频率分 = 0
基础分 = 40,000
短词加成 = 20,000

总分 = 60,000
```

## 数据存储

### 普通模式

用户学习数据存储在 `user_learning` 表：

```sql
CREATE TABLE user_learning (
    entry_id INTEGER PRIMARY KEY,
    access_count INTEGER NOT NULL DEFAULT 0,
    last_access_timestamp INTEGER NOT NULL DEFAULT 0,
    total_score REAL NOT NULL DEFAULT 0
);
```

### 过滤模式（隔离存储）

过滤模式使用独立表，避免污染普通模式排序：

```sql
CREATE TABLE filter_user_freq (
    filter_type TEXT NOT NULL,  -- 'e'（emoji）、'p'（模糊拼音）、's'（符号）
    code TEXT NOT NULL,
    word TEXT NOT NULL,
    frequency INTEGER DEFAULT 1,
    last_used REAL,
    PRIMARY KEY (filter_type, code, word)
);
```

## 算法特性

### 层级覆盖总结

| 层级 | 描述 | 用户可覆盖？ |
|------|------|--------------|
| P0 | 一级简码（jianma.txt 中 1 字符编码） | ❌ 永不 - 始终排第一 |
| P1 | 二级简码（jianma.txt 中 2 字符编码） | ❌ 永不 - 始终排在 P0 之后 |
| 1-4 | 常规层级 | ✅ 可以 - 通过层级覆盖加成 |

### 收敛行为

1. **短期**：时效分主导。刚选择的词在其层级内排第一。
2. **中期**（1-7 天）：时效分衰减，频率分变得重要。
3. **长期**（>14 天）：频率分和基础分主导。

### 用户体验

- **即时反馈**：选择的词立即跳到第一位（在其层级内）
- **学习**：常用词逐渐上升排名
- **遗忘**：少用词逐渐回落到基础排名
- **稳定性**：高频词即使最近未使用也能保持位置
- **简码保护**：1-2 级简码始终产生相同结果，保护肌肉记忆

### 性能

- 每个候选词的分数计算为 O(1)
- 用户数据缓存在内存中以快速查找
- 仅用户选择过的词条有 user_learning 记录（稀疏存储）

## 配置（AppConfig）

排序权重可在 `AppConfig.swift` 中自定义：

```swift
struct RankingWeights: Codable {
    var baseFrequencyWeight: Double = 1.0
    var fullMatchBonus: Double = 50000.0
    var lengthBonus: Double = 10000.0
    var wubiSourceBonus: Double = 5000.0
    var userLearningMultiplier: Double = 100000.0
    var recentSelectionBonus: Double = 500000.0
    var recentSelectionBoostTime: Double = 3600.0
    var recencyWeightWithinHour: Double = 4.0
    var recencyWeightWithinDay: Double = 2.0
    var recencyWeightWithinWeek: Double = 1.0
    var recencyWeightOlder: Double = 0.5
}
```
