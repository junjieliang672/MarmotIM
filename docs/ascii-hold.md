# ASCII 直通请求（ascii-hold）

外部程序可以在自己处于「快捷键模式」时，请求输入法把按键原样透传成 ASCII，
并在进入输入框时撤销这个请求。

## 要解决的问题

终端里的程序（文件管理器、分页器、lazygit、k9s、Vim 的 normal 模式）把单个字母
当命令用。中文模式开着的时候，`j` 根本到不了这些程序 —— 输入法先把它收进组字
缓冲区了。方向键和回车能过去，所以故障是**部分的**：一半能用一半不能用，很难
意识到是输入法的事。

这件事在程序那一侧修不了：按键压根没送到它那里。所以只能由程序主动告诉输入法。

反过来，整个终端一律关掉输入法也不行 —— shell 里、Claude Code 里还是要打中文的。
按 App 配「WezTerm 里永远英文」同样不行：快捷键模式和它的重命名框、搜索框是同一个
App、同一个 bundle id。真正需要的信号只有程序自己知道，所以只能由它来发。

## 协议

请求目录：

```
~/Library/Application Support/MarmotIM/ascii-hold/
```

- **请求**：建一个以自己进程号命名的文件，例如 `.../ascii-hold/54321`。
- **撤销**：把这个文件删掉。
- **生效条件**：目录里存在至少一个文件，其文件名恰好是一个仍然活着的进程号。

多个程序同时请求是集合语义：任意一个生效，整体就生效。

### 文件内容（可选）

空文件表示不限 App。要限定的话写一段 JSON：

```json
{"apps": ["com.github.wez.wezterm"]}
```

`apps` 里是 App 的 bundle id，也就是输入法看到的 client。**强烈建议写上**：程序留在
后台标签页里时通常还在快捷键模式，一条不限 App 的请求会让用户切到别的 App 之后
打不出中文，而症状（「中文输入坏了」）完全指不到发起请求的那个程序身上。

### 必须原子地创建

先写 `.<pid>.tmp`，再 `rename(2)` 成 `<pid>`。

直接 `creat()` 再 `write()` 的话，输入法可能正好在两步之间读到这个文件，看到空内容，
于是把一条本来限定了 App 的请求当成「不限 App」。`.<pid>.tmp` 这种名字不会被当作
请求，所以中间状态是安全的。

### 崩溃怎么办

不用管。输入法每次读取时都会用 `kill(pid, 0)` 验一遍，进程没了就把文件删掉。
所以 `kill -9` 一个正在请求的程序，最多一秒后请求自动失效。不需要守护进程，
不需要超时，也不需要客户端注册退出钩子。

名字解析不出进程号的条目（`.DS_Store`、`notes.txt`、`0`、`01`）既不会被当成请求，
也**不会被删掉** —— 这个目录不归输入法独占。

## 客户端最小实现

```sh
HOLD_DIR="$HOME/Library/Application Support/MarmotIM/ascii-hold"
mkdir -p "$HOLD_DIR"

# 请求（限定 WezTerm）
printf '{"apps":["com.github.wez.wezterm"]}' > "$HOLD_DIR/.$$.tmp"
mv "$HOLD_DIR/.$$.tmp" "$HOLD_DIR/$$"

# 撤销
rm -f "$HOLD_DIR/$$"
```

手工试一下的话，`touch "$HOLD_DIR/$$"` 就够了（不限 App）。

## 客户端该在什么时候撤销

1. **任何输入框拿到焦点时** —— 重命名、搜索、命令行、跳转。这是整个功能的意义所在：
   用户在这些地方还是要打中文。
2. **终端失去焦点时**。这是上面「限定 App」之外的另一道保险，而且更可靠：它在
   tmux、分屏、SSH 下都成立。终端的焦点上报是 DECSET 1004；Bubble Tea 用
   `tea.WithReportFocus()` 打开，然后处理 `tea.FocusMsg` / `tea.BlurMsg`。
3. **把终端交给子进程时**（编辑器、`sudo` 密码提示）。那段时间键盘不归你管。

superfile 的实现在 `src/pkg/ime/`，判断「现在是不是输入框」的地方在
`src/internal/typing_state.go`。

## 用户侧的开关

设置 → 基本 → **外部控制**，只有一个开关：

> **终端程序等快捷键时，自动按英文输入**（默认开）

下面一行状态，说明现在有没有程序在用。注意：客户端在终端失去焦点时就会撤销请求，
而你为了看这个设置页必须离开终端 —— 所以这里几乎总是显示「当前没有生效（N 秒前
用过，正常）」。**那是对的**，不是没生效。

反过来说，如果这一行显示「正在生效」，基本就意味着某个客户端卡住了（它已经不是
前台了却还挂着请求）。这时才会出现「强制解除」按钮。

另外，请求生效期间输入法菜单里会多一条灰掉的「英文直通（外部程序请求中）」。

### config.json 里的其余旋钮

这几个默认值就是对的，没有做成界面 —— 摆在设置页上只会让人不知道该不该勾。
真要改就手动编辑 `~/Library/Application Support/MarmotIM/config.json` 的 `asciiHold` 一节：

| 键 | 默认 | 说明 |
|---|---|---|
| `enabled` | `true` | 总开关，对应界面上那一项。 |
| `allowedApps` | `[]`（= 不限） | 只接受这些 App 里的请求。 |
| `requireAppScope` | `false` | 忽略没写 `apps` 的请求。 |
| `showIndicator` | `false` | 请求生效时在光标处弹提示。 |

## 和 shift 切换的关系

请求生效时按 shift 轻敲，会**顶掉**这条请求并切回中文，提示也如实显示「中」。

这里不能简单地让 shift 失效：那样一来敲第一下翻成英文（提示「英」，确实是英文），
敲第二下翻回去（提示「中」，但请求还按着，实际仍是英文）—— 一个显示「中」却在打
ASCII 的提示，和输入法坏了分不出来。

顶掉的效果在下面两种情况下清除：切换到别的 App（`activateServer`），以及请求本身
发生变化（程序撤销后重新请求）。文件管理器每次回到快捷键模式都会重新请求，所以
正常使用下 shift 的覆盖只在当次有效。

## 实现要点

读取侧在 `MarmotIM/Services/ASCIIHoldMonitor.swift`，判定逻辑抽成了纯函数
`ASCIIHoldRules`，测试在 `MarmotIMTests/ASCIIHoldTests.swift`。

两点值得知道：

- **正确性靠按键时的一次 `stat(2)`，不靠 DispatchSource。** 目录被删掉重建之后，
  原来的 fd 指向一个死掉的 inode，事件再也不来 —— 这是文件系统监视器的经典坑。
  如果正确性挂在监视器上，故障长相是「用了一周之后不灵了」。监视器只负责让反应
  提前到下一次按键之前发生。一次命中缓存的 `stat` 约 1 µs，比 `handle()` 本来就要
  做的一次候选检索低三个数量级。
- **不是用 Darwin 通知。** 通知是边沿触发、不带状态的：输入法重启就忘了（输入法由
  系统反复拉起），客户端崩在请求期间就再也没人发撤销 —— 中文输入永久失效且没有
  任何线索。文件是状态，随时可读，而且能自己收尸。

## 已知缺口：进程号复用

如果一条请求残留下来（客户端被 `kill -9`，而当时输入法没在运行，没人收尸），
之后系统的进程号绕回来又正好分给了别的进程，这条请求就永远不会过期。

要彻底堵上的话，客户端再写一个 `"startedAt": <unix 秒>`，输入法用
`sysctl(KERN_PROC_PID)` 取 `kp_proc.p_starttime` 比对。暂时没做：设置页里的
「立即清除所有请求」就是给这种情况准备的出口。
